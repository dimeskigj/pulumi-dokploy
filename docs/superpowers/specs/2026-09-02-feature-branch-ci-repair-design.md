# Feature Branch CI Repair Design

## User-directed amendment

The active branch is `feat/owned-ci-github-releases`, and the active build
filter is `feat/**`. The retained `feature/owned-ci-github-releases` and
`feature-owned-ci-github-releases` branches are aliases at the final commit.
This supersedes earlier `feature/` references in this document.

## Goal

Adopt the `feature/` branch namespace, repair the owned build workflow's remote
test failure, remove release dependencies that do not work in this repository,
and document the credentials maintainers must configure before publishing.

## Branch Migration

Rename the active local branch from `feature-owned-ci-github-releases` to
`feature/owned-ci-github-releases` and make the slash-named remote branch its
upstream. Change the build push filter from `feature-**` to `feature/**`.

Keep the existing `feature-owned-ci-github-releases` remote branch as an alias,
as requested, and update it to the same final commit. Do not modify the separate
`owned-ci-github-releases` branch.

## Build Failure

The SDK test step currently uses a folded YAML scalar:

```yaml
run: >-
  set -euo pipefail
  cd examples && $GO_TEST_EXEC ...
```

YAML folds those lines into one shell command. Bash therefore interprets
`cd examples` as positional arguments to `set`, then runs the SDK test command
from the repository root with paths intended to be relative to `examples/`.
This accounts for the near-immediate failures in every language job of GitHub
Actions run `33640089154`.

Use literal multiline shell blocks in the build, stable release, and prerelease
workflows so shell command boundaries are explicit. Add a workflow contract
test that parses the YAML and requires a newline between strict-mode setup and
the examples test command. Update the branch-filter contract test to require
`feature/**` and reject `feature-**`.

## Release Simplification

Remove the six Azure signing environment variables and `SKIP_SIGNING` from the
provider release steps. The current GoReleaser hook calls a no-op Make target,
so those values do not sign any artifact and should not be presented as release
requirements.

Remove `JAVA_SIGNING_KEY_ID` from Java publication. Gradle reads the armored
private key and passphrase but does not read a key ID.

Remove the stable release's Pulumi registry documentation dispatch job. It
targets Pulumi organization infrastructure, while this repository's owned Pages
workflow already publishes its generated documentation. Keeping the dispatch
would make an otherwise self-owned release depend on external organization
permissions.

Keep GitHub-hosted provider releases and package publication for npm, PyPI,
NuGet, and Maven Central.

## Credential Documentation

Add a release-credentials section to `CONTRIBUTING.md`. Maintainers configure
the values under **Settings > Secrets and variables > Actions > Repository
secrets**.

Required for package publication:

| Secret | Purpose |
| --- | --- |
| `NUGET_PUBLISH_KEY` | Publish the .NET SDK to NuGet.org. |
| `NPM_TOKEN` | Publish the Node.js SDK to npm. |
| `PYPI_API_TOKEN` | Publish the Python SDK to PyPI. |
| `JAVA_SIGNING_KEY` | ASCII-armored private PGP key used to sign Maven artifacts. |
| `JAVA_SIGNING_PASSWORD` | Passphrase for the Java signing key. |
| `OSSRH_USERNAME` | Sonatype Central publishing username or user token name. |
| `OSSRH_PASSWORD` | Sonatype Central publishing password or user token value. |

`CODECOV_TOKEN` is optional for coverage uploads. `GITHUB_TOKEN` is generated by
GitHub Actions and must not be added as a repository secret.

The documentation will state that all required publication secrets must be
configured before creating a stable or prerelease tag. It will also distinguish
these publication credentials from the separate protected secrets used only by
the manually dispatched live acceptance workflow.

## Verification

Run the workflow contract tests and the full Go test suite locally. Confirm that
the workflows contain no active `feature-**`, Azure signing, unused Java key ID,
or Pulumi registry docs-dispatch references.

Push the final commit to both feature branch refs. The push to
`feature/owned-ci-github-releases` must start the build workflow. Poll GitHub's
Actions API until that run completes and require a successful conclusion,
including every SDK test matrix job. If it fails, inspect the remote job data,
reproduce the failure where possible, fix it, and repeat until green.

Do not trigger stable or prerelease publication merely to validate this change:
those workflows publish irreversible external artifacts and cannot succeed
before the documented credentials are configured. Their structure and shell
commands are covered by local contract tests.
