# Schedule Resource Design

## Goal and constraints

Expose Dokploy scheduled commands as a first-class Pulumi `dokploy:index:Schedule` resource across the Go, Node.js, Python, .NET, and Java SDKs and generated reference docs. Support application, Compose, server, and Dokploy-server schedules. Users should be able to create, preview changes, update, refresh/import, and delete a schedule without silently adopting another schedule. Command execution is opt-in: `enabled` defaults to `false`. Treat `command` and `script` as secrets. Do not run live acceptance tests as part of routine validation.

The repository's checked-in `openapi/upstream.json` declares Schedule CRUD endpoints but gives `schedule.create`, `schedule.one`, and `schedule.list` empty response schemas. Read-only attempts to inspect Swagger on the configured `dokploy.dimeski.net` endpoint returned HTTP 403. Thus response bodies and whether create honors a supplied `scheduleId` remain unverified against a deployed server. The resource must not claim live compatibility from offline tests alone.

## Approach and alternatives

Generate a schedule ID in the provider, send it as `scheduleId` on create, and confirm ownership with `schedule.one`. This avoids ambiguous list matching and avoids requiring users to choose IDs. Reject a missing/mismatched read-back rather than adopting a schedule by name. Alternatives rejected: discovering by `schedule.list` (undocumented response and ambiguous duplicates), or requiring a caller-supplied ID (unnecessary user burden, without removing the server-contract uncertainty).

## Resource surface

Add `ScheduleArgs`, `ScheduleState`, and `Schedule` following existing infer resource patterns. Inputs: `name`, `cronExpression`, `command`; `scheduleType` with one of `application`, `compose`, `server`, `dokploy-server`; optional `description`, `appName`, `serviceName`, `shellType` (`bash` or `sh`), `script`, `timezone`, `organizationId`, `applicationId`, `composeId`, `serverId`, and `enabled`. The exact target-specific field constraints and defaults must reflect the checked-in request schema: validate the selected type and incompatible target IDs, do not demand an optional field without evidence that the API requires it, and document any target name required by actual server behavior if learned later. `enabled` defaults to `false`; `command` and `script` are marked secret in Pulumi schema and error handling must redact their values. Output includes stable `scheduleId` and refreshed server-observed fields. Avoid exposing or managing server-controlled `createdAt`.

Target identity (`scheduleType`, `applicationId`, `composeId`, `serverId`, and any other target-defining input established during implementation) is replace-on-change; name, cron, command, script, timezone, shell type, description, and enabled are in-place updates. Use delete-before-replace when necessary to prevent simultaneous execution of old and new schedules; keep ordinary changes in place. Preserve unknown/computed inputs in preview and reject known-invalid values before a network request.

## Client and lifecycle

Add `schedule.create`, `schedule.update`, `schedule.delete`, and `schedule.one` to `openapi/operations.txt`; add response and model corrections in `openapi/corrections.json` for the observed shape assumed by the implementation, retaining unknown JSON fields via `additionalProperties`. Derive the generated client with `make check_openapi` rather than editing generated code. `schedule.list` is not needed for ID discovery and `schedule.runManually` must never be invoked by resource lifecycle.

Create: return a preview without network calls on dry run; otherwise generate an ID, post the full request with `enabled: false` unless explicitly true, then read back that exact ID. If the ID cannot be confirmed, return an actionable error without attributing an unrelated schedule to Pulumi. Account for partial-creation risk: do not blindly retry creation or delete an unverified resource; preserve enough information for safe operator investigation while redacting secrets and IDs from logs. Read: query by stable ID, return absence only for a real not-found response, and refresh observable fields while retaining prior optional values only when the API omits them rather than explicitly clearing them. Update: send the requested mutable configuration and verify or refresh the same ID; no command execution endpoint is called. Delete: delete by stable ID with existing provider conventions for already-absent resources. Error messages must not reveal command/script contents, credentials, private URLs, or resource IDs.

## Testing, docs, and evidence

Write focused failing tests before implementation: OpenAPI correction/generation, schema token and secret annotations, checks for all four target types and computed values, defaults and target validation, diff replacement versus update, dry-run behavior, exact request fields, create ID verification failures, read drift/not-found/malformed responses, update, delete, and redaction. Cover each target with mock HTTP lifecycles and extend safe live acceptance fixtures only as an opt-in test, never run them routinely. Include a disabled Schedule example and a warning that enabling it can execute shell commands on a workload or server; regenerate SDKs/schema and website reference docs from source.

Use the applicable Makefile checks (`make lint`, `make test_provider`, `make test_race`, `make provider`, `make check_openapi`, `make check_codegen`, `make build_sdks`, `make test_examples`, `make docs_check`) plus `git diff --check` and status/diff inspection, reporting checks not run. Never run live acceptance against production or as an incidental check. Before claiming live Schedule support is verified, obtain sanitized response-shape evidence on a dedicated non-production server using the acceptance safety procedure in `tests/README.md`. Offline tests establish only the assumed contract.

Existing uncommitted changes in the release-smoke workflow and release/schema tests/scripts are unrelated and must be preserved. Generated outputs are regenerated only after checking for uncommitted changes in their directories.
