title: Applications
description: Create and update Dokploy applications from Docker, Git, GitLab, GitHub, Gitea, or Bitbucket sources.
---

Create a Docker application by selecting the `docker` source variant. A Project owns the default production Environment; use an explicit Environment when this application belongs in staging or another non-production target.

```typescript
const app = new dokploy.Application("web", {
  name: "web",
  environmentId: environment.environmentId,
  source: { type: "docker", docker: { image: "nginx:latest" } },
});
```

For a public Git repository, select `type: "git"` and provide the URL, branch, and build settings:

```typescript
const gitApp = new dokploy.Application("git-web", {
  name: "git-web",
  environmentId: environment.environmentId,
  source: {
    type: "git",
    git: { url: "https://github.com/example/web.git", branch: "main", build: { type: "nixpacks" } },
  },
});
```

## Repository sources and builders

Use exactly one source variant. `github`, `gitea`, `bitbucket`, and `gitlab` refer to existing Dokploy integrations; this provider does not create or manage those integrations. For an existing GitLab integration, set `type: "gitlab"` and provide the project metadata. GitHub's optional `triggerType` accepts `push` (the default) or `tag`. Bitbucket requires `repositorySlug` in addition to the integration, owner, repository, and branch. Keep integration and repository identifiers in Pulumi configuration rather than source code.

All six builders are available for Git, GitLab, GitHub, Gitea, and Bitbucket repository sources. Builder-specific options are:

| Builder (`build.type`) | Options |
| --- | --- |
| `dockerfile` | Required `dockerfile`; optional `dockerContextPath` and `dockerBuildStage` |
| `nixpacks` | Optional `publishDirectory` and `isStaticSpa` |
| `heroku_buildpacks` | Optional `herokuVersion` |
| `paketo_buildpacks` | No builder-specific options |
| `static` | Optional `isStaticSpa` |
| `railpack` | Optional `railpackVersion` |

`publishDirectory` applies to Nixpacks; `isStaticSpa` is supported by Nixpacks and Static. Do not pass options belonging to a different builder. Docker image sources do not use repository build settings.

This checked TypeScript example reads integration and repository identity from stack configuration and configures an SPA with Nixpacks:

```ts
const config = new pulumi.Config();
const builderExample = new dokploy.Application("nixpacks-static-spa", {
  name: "nixpacks-static-spa",
  environmentId: config.require("environmentId"),
  autoDeploy: false,
  source: {
    type: "github",
    github: {
      integrationId: config.require("githubIntegrationId"),
      owner: config.require("githubOwner"),
      repository: config.require("githubRepository"),
      branch: "main",
      triggerType: "push",
      build: { type: "nixpacks", publishDirectory: "dist", isStaticSpa: true },
    },
  },
});
const gitlabExample = new dokploy.Application("gitlab-example", {
  name: "gitlab-example",
  environmentId: config.require("environmentId"),
  source: {
    type: "gitlab",
    gitlab: {
      integrationId: config.require("gitlabIntegrationId"),
      projectId: config.requireNumber("gitlabProjectId"),
      owner: config.require("gitlabOwner"),
      namespace: config.require("gitlabNamespace"),
      repository: config.require("gitlabRepository"),
      branch: "main",
      build: { type: "nixpacks" },
    },
  },
});
```

`autoDeploy` is optional. Omitting it leaves Dokploy's current/default value unmanaged; setting `false` disables automatic deployment triggers, and setting `true` enables them. This does not suppress the provider's explicit deployment during create or runtime source/build updates. Changing only `autoDeploy` is configuration-only and does not fetch, build, deploy, or redeploy the application. GitHub `push`/`tag` selects the integration trigger; it is distinct from the provider's explicit deployment lifecycle.

Creates and runtime source/build updates fetch the selected source and wait for deployment completion. A source discriminator change replaces the Application; `environmentId` and `serverId` are also replacement-only. Other metadata and source settings update through the normal Pulumi diff. The Project/Environment is a dependency; external integrations remain unmanaged, while SSH keys can be managed by this provider. See [sources](../../concepts/sources/) and the [Application reference](../../reference/application/).

The optional live Application configuration coverage creates bare fixtures and tests configuration persistence only: it never clones, fetches, builds, deploys, or redeploys. Generic Git covers all six builders; GitHub, Gitea, Bitbucket, and GitLab cases run only when their protected integration/repository prerequisites are supplied, and otherwise skip individually. A configuration-only pass does not establish compatibility with external repository cloning or builds.

For a generic Git source, supply an existing `SSHKey` through its `sshKeyId`.
For published application ports, use the configuration-only [`Port` resource](../ports/); a Port change does not trigger deployment.
Applications may reference a managed `Registry` with `registryId` for deployment
images and `buildRegistryId` for build images. Registry credentials are secret
inputs and the provider tests the registry before creating or updating it.
