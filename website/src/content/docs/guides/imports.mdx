---
title: Imports
description: Adopt existing Dokploy resources into Pulumi state.
---

Import with the Pulumi resource type token and existing Dokploy ID:

`Port` imports use only the Dokploy port ID; the application relation is read from the imported resource:

```bash
pulumi import dokploy:index:Port mapping <port-id>
```

An ambiguous 400 “Port not found” response may indicate lost permission; refresh does not discard state on that response.

```bash
pulumi import dokploy:index:Project existing p1
```

Review the generated state, then run `pulumi refresh` to compare it with Dokploy before making changes. Imported resources may omit write-only values such as passwords. Restore those secret inputs with `pulumi config set --secret` before a future update; the provider cannot recover a write-only password from Dokploy.

If the imported object no longer exists, refresh removes it from state and a subsequent `pulumi up` can recreate it. See [lifecycle and state](../../concepts/lifecycle-and-state/) and [Secrets](../../concepts/secrets/).

SSHKey, Registry, Tag, and Mount resources import with their Dokploy IDs:

```text
pulumi import dokploy:index:SSHKey key <ssh-key-id>
pulumi import dokploy:index:Registry registry <registry-id>
pulumi import dokploy:index:Tag tag <tag-id>
pulumi import dokploy:index:Mount mount <mount-id>
pulumi import dokploy:index:Server remoteServer <server-id>
```

The Server import ID is its Dokploy server ID. See the [Servers guide](../servers/) for its configuration-only lifecycle and safety limits.

`ProjectTag` is an association, so its import ID is `<project-id>/<tag-id>`:

```text
pulumi import dokploy:index:ProjectTag projectTag <project-id>/<tag-id>
```

Import a notification using its Dokploy notification ID, not the selected channel relation ID:

```text
pulumi import dokploy:index:Notification notification <notification-id>
```

The provider discovers the channel and active organization during import. Required
secret fields omitted from Dokploy's response cannot be recovered on fresh import;
they appear as empty secret values. Supply them from protected configuration with
`pulumi config set --secret` before updating, never send the empty credentials.
Refresh before repairing partial state; see the [Notifications guide](../notifications/).
`GitLabIntegration` imports by its GitLab relation ID, not by the OAuth
application ID or parent Git-provider ID:

```text
pulumi import dokploy:index:GitLabIntegration integration <gitlab-id>
```

An incomplete imported integration may require resupplying the client secret
before update. Import leaves existing sharing unchanged, and no tokens are
exported. Before deleting an integration, inspect unmanaged workloads that may
reference it. If create success is uncertain, inspect Dokploy before retrying.
See the [GitLab integrations guide](../gitlab-integrations/).

Gitea and Bitbucket integrations also import by their relation IDs, not parent
Git-provider IDs:

```text
pulumi import dokploy:index:GiteaIntegration gitea <gitea-id>
pulumi import dokploy:index:BitbucketIntegration bitbucket <bitbucket-id>
```

Gitea's OAuth application and authorization are configured manually outside
Pulumi. Bitbucket imports may represent incomplete or legacy credential state;
the active credential must be supplied as a Pulumi secret before an update.
Review provider-specific optional-field semantics and unmanaged workload
references before changing or deleting either integration. See the
[Gitea integrations guide](../gitea-integrations/) and
[Bitbucket integrations guide](../bitbucket-integrations/).
